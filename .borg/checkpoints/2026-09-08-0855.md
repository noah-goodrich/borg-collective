## 2. Accomplished

**Both pricing bugs fixed**, in `/Users/noah/dev/claude-plugins/token-cost/hooks/token-spend-log.sh`:

1. **Tier miss in `_costof`.** The regex `opus-4-[6-9]` does not match `opus-5`, so every Opus 5 session fell
   through to the generic `opus` arm and billed at the historical $15/$75 — the direct cause of `borg spend`
   reading ~3× high. Widened to `opus-5|opus-4-[6-9]`. Also added a `sonnet-5` arm **ahead of** the generic
   `sonnet` arm: Sonnet 5 is $2/$10, *cheaper* than Sonnet 4.6's $3/$15, so the generic arm over-billed it —
   an error in the opposite direction from the Opus one, which is why it needed its own arm rather than a
   widened regex.
2. **Blanket cache-write rate.** The single `w:` column priced every cache write at 1.25× input. Real rates
   are 1.25× for a 5-minute TTL and **2× for 1 hour**. Verified against live transcripts in
   `~/.claude/projects/-Users-noah-dev-borg-collective/`: `cache_creation.ephemeral_1h_input_tokens` carries
   the full write and `ephemeral_5m_input_tokens` is 0 on every sampled record — so essentially every write
   was under-priced by 1.6×. Replaced with `w1h:`/`w5m:` columns per tier.

**Pricing verified against the `claude-api` skill**, not recalled: Opus 5 $5/$25, Sonnet 5 $2/$10,
Sonnet 4.6 $3/$15, Haiku 4.5 $1/$5, Fable 5 $10/$50; cache write 5m = 1.25× input, 1h = 2× input, read = 0.1×.

**Schema 2 → 3, additive only (expand phase).** `cache_creation_1h` and `cache_creation_5m` were added to
every `by_model` and `by_type` block **alongside** the unchanged `cache_creation` total, read from
`usage.cache_creation.ephemeral_{1h,5m}_input_tokens` in `_bymodel` and `_bytype`. A schema-2 reader is
unaffected. `borg spend` (`borg.zsh`, `cmd_spend`) does not gate on `schema` — it sums the stored
`.main.est_cost_usd` / `.subagents.est_cost_usd` — so the bump breaks nothing.

**Old records are not silently re-priced.** `_costof` uses the TTL split only when `cache_creation_1h +
cache_creation_5m > 0`; otherwise it falls back to `cache_creation * w5m`, the old assumption. A record whose
transcript predated the nested `cache_creation` object keeps the rate it was written under.

**10 new bats cases** in `token-cost/hooks/test/token-spend-log.bats`, in the same commit-to-be per the

key-presence check that the split sits beside the unchanged total. Full suite: **51/51 pass, 0 failures.**

**Answered `borg link --refresh`** (read from source, not inferred): it runs `cmd_scan --llm` *before*
building the document — unrelated to the sweep or the page. Per registered project it locates the latest
session JSONL and pipes it through `summarize.py --llm`, which shells to `claude --model haiku` on the last
~30 exchanges of the last 200 lines, writing the result to that project's registry `summary` field. Two
properties matter: there is **no staleness gate** (every project with a findable transcript is re-summarized
every run, touched or not), and the loop is **sequential**. So it is cheap in dollars (Haiku, small inputs,
~20 projects) and expensive in wall-clock. Recommended cadence: **once each morning, on demand, before the
first `borg link`** — not a launchd job. A staleness gate (skip when transcript mtime predates the stored
summary) would turn a 20-call refresh into a 2-call one and make "run it every time" viable; worth a
directive if the morning latency becomes annoying.
