## 4. Blockers

**No blockers for AC5.** Everything below is now a filed directive in `docs/plans/directives/` — recorded here because
the reasoning matters, not because anything is stuck:

- **`echo … | jq` is repo-wide** — 36 sites in 7 functions in `borg.zsh`, plus 5 in `lib/desktop.zsh`. Only `cmd_ls`
  and `_borg_do_switch` were fixed. **`borg switch` to a project with no registered tmux window still dies exit 5
  inside `cmd_status`** — measured, not inferred.
- **The fzf preview is a ghost.** `grep -c -- '--preview' borg.zsh` returns 0, yet it is cited as a live consumer in
  ~10 places — and `PICTURE_BUDGET = 68`'s entire rationale is the 70-column pane that no longer exists.
- **The auto-memory gate's FAIL is untrustworthy.** Its numerator is a `PostToolUse(Read)` hook, but `MEMORY.md` is
  injected into the system prompt and recalls arrive in `<system-reminder>` blocks — neither is a tool call. Do not
  move the pre-registered 0.2 threshold; fix the numerator or retire the gate.
- **Two mistakes of mine worth carrying.** (1) I asserted in a workflow brief that `render.porcelain()` feeds
  `borg switch`'s picker. It does not — `cmd_ls --porcelain`, a separate zsh implementation, does. The builder
  propagated my claim into a commit message and three docstrings before a reviewer caught it. (2) A later round
  credited a named test with pinning a fork; mutation showed the string was a *docstring sentence* and the test
  survived deleting the fork. **Both are the same failure: a plausible causal claim asserted instead of demonstrated.**
  The standing rule that came out of it — run the command before writing "X consumes Y" — is worth keeping.
- **Line pins produced a defect in every single review round**, and each fix wrote a fresh wrong number
  (`borg.zsh:3111` → `:3064` → `:3182`, none correct when written). Anchoring by symbol or test name is now the
  convention; saved to memory as `reference_line_pins_rot_anchor_instead`.

## 5. Next Session

**Start AC5: lifecycle skills author project manifests by default.** This is the work that makes the viz layer
*useful* rather than merely correct.

The measurement that motivates it: **2 of 20 registered projects have a manifest**
(`stillpoint/.borg/programs/ingle-t1-cutover.json` and `borg-collective/.borg/programs/viz-program.json`). Everything
shipped today — the grid, `▸ NEXT`, yours-vs-mine routing, the freshness line — reads from those files. With two, the
page renders near-empty and reads as broken no matter how correct the renderer is. `PROJECT_PLAN.md`'s own Risks
section called this in advance: *"the authoring path is load-bearing, not the renderer."*

AC5's three pieces, none opt-in:
- `/borg-plan` scaffolds a manifest — `skills/borg-plan/SKILL.md`
- `/borg-link-up` updates row status — `skills/borg-link-up/SKILL.md`
- `/borg-assimilate` closes rows — `skills/borg-assimilate/SKILL.md`

Its verify clause requires eval cases running each skill headless against a fixture repository, **each positive case
paired with a negative proving the conditional discriminates** (the `evals/s4-k3/run.sh` E4/E5 pattern). That overlaps
AC6's harness, so decide early whether to build the harness first or inline the cases and generalize after.

**Do not wait for evidence that manifests get used before automating their capture.** That is the voluntary-capture bet
cairn already lost — saved as `feedback_hardwire_dont_wait_for_evidence`.

Cheap bridge if the page needs to be useful before AC5 lands: hand-write manifests for the three or four repos touched
weekly. ~20 minutes, and it makes the board real in the meantime.
