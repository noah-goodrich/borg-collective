CI was red on **all five** PRs, on **both** bats lanes. Two independent harness bugs — neither in
`borg.zsh`. The last checkpoint predicted only the flaky `watch` test; the second one was failing 5/5
deterministically and was the harder of the two.

**Bug 1 — `watch` waited for the wrong thing** (`tests/cli_contract.bats`). The poll condition was
`[ ! -s "$outfile" ]`, which goes false the instant the `BORG WATCH` header lands (`borg.zsh:2646`), but the
assertions also need `cmd_link`'s body (`:2650`) and `RECENT NANOPROBES` (`:2653`). `cmd_link` shells out to
jq/tmux repeatedly, so on a loaded runner the kill landed mid-frame. Now waits on `Ctrl-C to exit` (`:2670`),
the last line a frame emits. Measured: a complete frame lands in **one 50ms poll tick** against the raised
200-tick ceiling — a 200x margin, not a tuned guess; interval 10s -> 30s so the ceiling still cannot reach a
second frame. Confirmed `ok 47` on the macOS runner that had been failing it. It never failed on ubuntu,
which fits the slow-runner race exactly.

**Bug 2 — an early-closing pipe corrupted `$output` with zsh's EPIPE diagnostic.** The fzf-producer test read
column 1 of row 1 as `borg link --porcelain | head -1 | cut -f1`. `head` exits after one line;
`_borg_link_porcelain`'s printf loop (`borg.zsh:273`) then takes EPIPE on the next row, and zsh **reports**
the failed write rather than dying silently:

```
first field was [echo
_borg_link_porcelain:printf:28: write error: broken pipe
_borg_link_porcelain:28: write error: broken pipe] (status 0)
```

`bats run` merges stderr into `$output`, so the exact-match assertion saw the row plus two diagnostics.
Green locally / red on both CI lanes because whether the next write loses the race to `head`'s exit is
timing-dependent — the green-locally/red-on-CI class this file exists to catch, arriving in the harness
rather than in the CLI. Fixed by dropping the pipe and reading bats' own `$lines` over an unpiped
`run_zsh_borg`, the same invocation shape the golden assertions already use.

**What cracked it: the byte-exact golden for the same command passed in the same CI job.** That proved
stdout was correct and forced the conclusion that the corruption was stderr — the alternative (a sort
regression) was ruled out by construction, not by guessing. The `od -c` diagnostic added to the assertion
(mirroring `_assert_link_golden`'s existing pattern) is what produced the quote above; it is kept.

**Verified non-vacuous rather than trusted because it passes**: dropping the pinned-first sort key
(`borg.zsh:256`) still fails the replacement, reporting `first field was [bravo]`. Swept the suite for the
same trap elsewhere — the other `head -1 | cut` uses read files via `grep` inside `$(...)`, which captures
stdout only, so they are immune by construction. Only `run` + slow producer + early-closing consumer bites.

**Stack landed by rebase, not by re-merge.** `delete_branch_on_merge` is false, so GitHub does not
auto-retarget children. Each PR was retargeted to `main` with `gh pr edit --base main`, then rebased with
`git rebase --onto origin/main <original-parent-tip>` so only its own single commit replayed (squash-merging
the parent means the parent's commits must NOT be replayed). Every rebase was verified with `git range-diff`,
which reported `=` (patch preserved byte-for-byte) in all four cases, and each PR's CI was confirmed green
before its merge.
