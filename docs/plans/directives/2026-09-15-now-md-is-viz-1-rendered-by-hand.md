# Directive: NOW.md is viz-1's output, rendered by hand — keep it until viz-1 ships

*Parent plan: 2026-08-24-one-front-door-link-derived-fact-surface*
*Filed: 2026-09-15 · Status: DETERMINATION — proposed, awaiting Noah*

**tl;dr** — `~/dev/NOW.md` is not a competing front door. It is
`docs/plans/directives/2026-08-11-viz-1-awaiting-you-tier.md`'s output, produced by hand because
viz-1 was never built. It should be retired INTO `borg link` when viz-1 ships, and not before — and
it should not move into the merge-tree hub, whose renderer was superseded on 2026-08-24. Two
corrections to the framing that produced this question are recorded below, because both were
load-bearing and both were wrong.

## The determination

**NOW.md is viz-1's output.** viz-1's objective, verbatim: *"Surface work that is blocked on Noah as
its own labeled tier, ahead of all ranking, in both the live renderer and `borg link`. Distinguish
blocked-on-you from blocked-on-others in the data model, because collapsing them is what hid the
most actionable work on the board."* NOW.md's top section is a numbered "Do these" table of rows
each blocked on Noah, with an action and a deadline. That is the same artifact with a hand-built
data model.

**And it confirms viz-1 rather than competing with it.** viz-1 cites 2026-08-10, where
`sme-self-service-pat` was suppressed despite its author annotating the blocker as non-technical.
That project closed 2026-09-15 — and the surface that carried it to a decision was NOW.md, by hand.
So viz-1's thesis is validated in production and its mechanism is still unbuilt. A hand-maintained
stopgap that demonstrably worked is evidence FOR the directive, not a defect competing with it.

## Why it keeps its hands for now

`PROJECT_PLAN.md`'s objective says `borg link` is "the single front door", so a second
hand-maintained front door reads as a defect. It is one — eventually. It is not one yet, because
**neither viz-1 nor viz-3 has ever been implemented**: zero mentions in `docs/plans/assimilated/`,
both filed 2026-08-11 and untouched since. Retiring a working hand-built surface in favour of an
unbuilt directive produces neither surface, which is strictly worse than the duplication.

So: NOW.md and `NOW.html` stay hand-maintained, and viz-1 absorbs them when it ships. The
duplication is a KNOWN and DATED debt rather than an oversight, which is the only part of it that
was actually missing.

## Why NOT the merge-tree hub

The alternative under consideration was folding NOW.md into
`~/.local/state/borg/merge-tree/`, whose `index.html` it was said to duplicate. Rejected on two
grounds:

1. **That renderer is superseded.** `graph.html`'s Frozen Atlas / ELK design was superseded
   2026-08-24 by the One Front Door plan's boundary — "NOT building: S1 `borg show`, and the `--md` /
   `--html` output modes. **ANSI-to-stdout only. Conscious call**" — and closed out as such in
   [#194](https://github.com/noah-goodrich/borg-collective/pull/194), with the kill-test's verdict
   recorded there for the first time. Folding a live surface into a retired one is not consolidation.
2. **viz-1 names BOTH surfaces anyway.** Its objective is "in both the live renderer AND
   `borg link`", so moving NOW.md into the hub would relocate the duplication rather than resolve it.

`NOW.html` therefore stays where it is, generated by `~/dev/bin/{linkify,md2html}.py` +
`refresh-docs.sh`, until viz-1 renders the same tier from derived fact.

## Two corrections to the framing

**(1) "A manifest row must resolve to a ref borg can sweep" is FALSE.** This was the premise behind a
proposed AC5 scope change, and it does not survive measurement. `refs.ref_kind` accepts three
anchored vocabularies — `github` (`owner/repo#num`), `jira` (`^[A-Z][A-Z0-9]*-[0-9]+$`) and `link`
(`^https?://\S+$`) — and all nine of NOW.md's rows validate as manifest rows TODAY:

| Row kind | Example | `ref_kind` | `core.validate` |
|---|---|---|---|
| Jira ticket | `DE-2107`, `DE-2103` | `jira` | VALID |
| PR | `acme/infra#2411`, `acme/sfp#412` | `github` | VALID |
| Slack message | a permalink | `link` | VALID |
| Vendor console | a console URL | `link` | VALID |
| HR system | a Lattice URL | `link` | VALID |

Unknown row keys are tolerated AND persisted — `{owner, due, blocked_on}` validates, because
`core.declared_body` strips by `_`-prefix rather than by a name list. So the "unsweepable row" shape
(title, owner, blocked-on-whom, date, optional external link) needs no schema change. It is already
expressible.

**(2) The real defect is narrower and already shipped: the jira wedge.** Admissibility was never the
problem; BEHAVIOUR is. Measured:

```
link parent    -> SKIPPED. The child stays ready. Deliberate, via refs.is_reference, and
                  ready_set's docstring records the measurement that motivated it.
jira parent    -> WEDGES THE CHAIN FOREVER.
github parent  -> wedges when unresolvable, which is correct; it should have resolved.
```

`refs.expects_github` classifies a jira key as TRACKED — *"real work with real state"* — so it blocks
its children like any parent. But `states` is fed only by sources in
`grid.RESOLVED_STATE_SOURCES = (swept, fetched)`, `lib/recon/adapters/` contains exactly one adapter
(github), and nothing in the recon surface knows jira. A jira row's state is therefore permanently
unknown, and `ready_set`'s own rule is "unknown is not merged".

**And borg is silent about it by design.** `expects_github`'s docstring: a jira key *"is still none of
a GitHub GraphQL query's business, so its absence from that query is not a degradation and must not
print a `▸ SIGNALS` line on every render."* The reasoning is sound and the outcome is not: put
`DE-2107` at order 1 of a lane and every row behind it is wedged forever, with no signal on the page.
A confident wrong answer with no warning — the defect class this plan has spent nine decisions on,
already shipped rather than hypothetical.

## Proposed amendment to AC5 — one sentence, not a scope change

AC5 does not need to admit a new row shape. What its text does not say is which of the three kinds
the lifecycle skills may WRITE. Proposed, additive, touching no ratified decision:

> The three verbs author `github` rows only. `jira` and `link` refs remain hand-authored: a `link`
> row is inert by design (`ready_set` skips it), but a `jira` row is TRACKED with no adapter to
> resolve it, so an auto-authored jira row would wedge every row behind it with no `▸ SIGNALS` line.
> Admitting jira to the writer is gated on a jira adapter existing, not on this criterion.

Noah holds the lock on acceptance criteria. This is a proposal, not an edit — `PROJECT_PLAN.md` is
untouched by this PR.

## The overlap is TWO surfaces, not three

Worth finding now rather than after something is built:

- **viz-1 and viz-3 are the same mechanism described twice.** Both cite the same motivating incident
  (2026-08-10, a single score burying the right answer). viz-1 says "its own labeled tier, ahead of
  all ranking"; viz-3 says "three tiers rather than one score". Both are unbuilt. They should be
  collapsed, or their boundary stated, before either is implemented.
- **The merge-tree hub is already resolved by supersession** — `▸ CHAINS` in `borg link` is viz-3's
  mechanism shipped, on the ANSI surface that replaced the hub. So the live count is TWO (`borg link`,
  NOW.md), and viz-1 is what merges them.

## Scope Boundaries

- **NOT** retiring NOW.md or `NOW.html` now. That happens when viz-1 ships.
- **NOT** implementing viz-1 or viz-3, and **NOT** collapsing them — that is named as work, not done
  here.
- **NOT** editing `PROJECT_PLAN.md`. The AC5 amendment above is a proposal.
- **NOT** building the jira adapter. Scoped separately; it is the thing that would unwedge jira rows,
  and `swept` is already in `RESOLVED_STATE_SOURCES`, so an adapter is sufficient — no core change.
