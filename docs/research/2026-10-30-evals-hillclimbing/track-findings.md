## Track 1: how to design and run evals, tier by tier

- Use the cheapest grader that works, and a judge only when no check can decide. Anthropic's hillclimbing post says to use a code check when outputs are constrained and, when a judge is needed, to write the rubric as checkable claims and not use the model under test as the judge. UK AISI limits model grading to content matching. Hamel Husain: CI should favor deterministic checks. (t1-anthropic-hillclimbing, t1-aisi-evaluation-standard, t1-hamel-evals-faq)
- Saturated capability cases graduate into the regression suite. When a baseline scores about 95% or more, a hillclimb should target cost or latency, not quality. (t1-anthropic-demystifying-evals, t1-anthropic-hillclimbing)
- Small-n statistics: normal-approximation error bars understate uncertainty below a few hundred items; use Wilson or Bayesian intervals and paired comparison of variants on the same cases. A 10/10 result has a 95% Wilson lower bound of about 72%. Refuse to hillclimb when the eval's noise exceeds the smallest effect you would act on. (t1-bowyer-clt-small-n, t1-anthropic-statistical-evals)
- pass@k means at least one success in k tries; pass^k means all k succeed. tau-bench showed agents falling below 25% on pass^8. Inspect AI exposes the choice as a reducer per sample. (t1-tau-bench-passk, t1-inspect-metrics)
- Validate judges by per-class rates (true-positive and true-negative rate) on 100 to 200 human labels per failure mode, split into train, dev and test with 30 to 50 passes and 30 to 50 fails in each. Use binary verdicts and one judge per failure mode. Kappa beats percent agreement. (t1-hamel-evals-faq, t1-eugeneyan-llm-evaluators, t1-thakur-judging-judges)
- Judge biases: position, verbosity, self-preference. Mitigate by randomizing order, controlling length and using a different judge model. (t1-zheng-mt-bench, t1-panickssery-self-preference, t1-ye-calm-biases, t1-openai-eval-best-practices)
- Trigger evals: about 20 queries, half should-trigger and half should-not, near-miss negatives being the most valuable; 3 runs per query, a 60/40 train and held-out split, at most 5 iterations. "One-sided evals create one-sided optimization." (t1-anthropic-skill-creator, t1-anthropic-demystifying-evals)
- Contradicting evidence: judges are weaker than agreement numbers suggest on hard correctness pairs (t1-judgebench, t1-dorner-judge-twice-data). The two statistics sources disagree at small n. Anthropic's own worked example held out 14 cases, and skill-creator's held-out set is 8 queries, from which it picks the best of up to 5 descriptions, so its held-out score is biased upward.
- Not found: a primary source on flakiness quarantine for LLM evals, concrete CI-versus-nightly budgets, or contamination practice for private hand-written sets.

## Track 2: adopt or build

- Adopt `claude plugin eval` for the Claude plugin side. It supports regex, tool_used, tool_order, file_exists and LLM graders that vote 2 of 3, runs each case 3 times by default, scores against a no-plugin baseline, and supports `--max-cost-usd`, pinned models, versioned JSON and CI exit codes. It cannot run custom-code graders, run any agent other than `claude -p` (so no Cortex), report confidence intervals, split train and test, or keep history. (t2-claude-plugin-eval-docs)
- Adopt skill-creator's `run_loop.py` for description hillclimbing: it drives `claude -p`, splits 60/40, runs each query 3 times and picks the winner by held-out score. Its case format is incompatible with plugin eval's. (t2-skill-creator-skillmd, t2-skill-creator-blog)
- Wrap, trial first: `/claude-api build-eval` and `/claude-api hillclimb` (shipped 2026-09-28) for skill bodies and agent definitions. One change per round, a test set the optimizer never sees, confidence intervals reported. How it stores round history is not documented, and Hamel Husain found its evaluator over-bundled. (t2-claude-api-build-eval-hillclimb, t2-hamel-claude-auto-evals)
- Wrap promptfoo only if a Claude-and-Cortex matrix becomes necessary: MIT licensed, last release 0.125.1 on 2026-10-25, a Python provider can return token usage and cost. No documented run-level spend cap, no confidence intervals, no train and test split, and Node is a new runtime. (t2-promptfoo-assertions-cli, t2-promptfoo-claude-agent-sdk-provider, t2-promptfoo-repo-releases)

- Cheapest result history: append one JSONL line per run (case id, git SHA, arm, pass or score, cost, turns, seconds); the model id comes from the `system/init` event and cost with a per-model breakdown from the final `result` message of headless Claude; archive each `aggregate-result.json` from plugin eval; one stdlib Python script (about 50 lines, the track's estimate) computes Wilson intervals and per-SHA trends. ## Track 3: hillclimbing

- Anthropic's loop: split cases at random into train and test; check the eval's noise is below the smallest gain worth acting on; propose one patch per round that fixes a failure at its root; keep it only if train and test both improve; revert if test is flat while train rises, or on any regression; stop when the score stalls for two or three rounds; report the test result with confidence intervals and recommend against merging if the gain is within noise. Its example used 30 search cases plus 14 held out. (t3-anthropic-hillclimbing-blog)
- Anthropic already ships a trigger-description optimizer: 20 labeled queries, a stratified 60/40 split, 3 runs per query, up to 5 iterations, test scores stripped from the optimizer's history. The winner is chosen by test score, so the test set doubles as a selection set; nothing is sealed. (t3-skill-creator-run-loop)
- One rewrite does almost all the work: on 9 production skills a single rewrite fed the wrong-trigger and missed-trigger cases matched hand-tuned descriptions (79.2% against 79.4% F1); more iterations changed F1 by less than 0.5%. A large train and validation gap meant overlapping skill scopes, and the fix was restructuring the skills. (t3-single-rewrite-skill-descriptions, preprint)
- Optimizing at small n made things worse: with 30 training examples GEPA's optimized prompts scored 34.0% on test against 62.4% for the unoptimized start. No reflective optimizer beat a well-written fixed prompt. Train scored 5 to 20 points above test even at about 262 examples. (t3-mage-low-data-overfit, preprint; t3-opro-overfitting)
- GEPA is the strongest optimizer family (ICLR 2026): over 10 points above MIPROv2, prompts up to 9.2 times shorter, but it used 111 to 300 validation examples and thousands of runs. Skills learned by gskill transferred to Claude Code using about 200 train and 50 validation tasks. (t3-gepa-paper, t3-gskill-learning-skills)
- Shrinking tokens needs a Pareto front, not a weighted score. Optimizers that favor brevity drop domain detail, and repeated full rewrites erode content. (t3-craft-pareto, t3-ace-context-collapse)
- Gaming is real but visible: optimizers have read cached answer keys, and a broken prompt won through a silent parser fallback. Recommended guards: deterministic gates the judge cannot override, frozen holdouts, canary cases where a perfect score means cheating. Exploits found by optimizing prompts were spelled out in plain language, so a human reviewing the diff catches them. (t3-llm-judge-not-oracle, t3-mats-misalignment-legible)
- Optimized prompts do not carry across models. A prompt tuned on one model often does substantially worse on another. (t3-promptbridge-model-drift, preprint)
- The track's own arithmetic, not from a source: 10 cases at 80% gives a 95% interval of about plus or minus 25 points; a 40% hold-out of 10 is 4 cases, so one case flipping moves the score 25 points; repeating runs reduces noise within a case but adds no cases. A full description run at skill-creator's defaults is about 300 trigger checks.
- Contradicting evidence: gskill reports transfer across models, against PromptBridge. GEPA reports shorter prompts generalize better, ACE reports brevity bias. Anthropic presents hillclimbing a skill body as a success (66% to 88%) without giving the case count.
- Not found: any published minimum case count for hillclimbing; dollar cost per round for DSPy or GEPA; TextGrad and APE effect sizes; any result on optimizing for Cortex Code or Snowflake.

## Track 4: Cortex Code portability

- Cortex Code's documented extension surface is Claude-shaped: SKILL.md skills, Markdown and YAML agents, hook events with Claude names; it also reads `.claude/skills`, `.claude/agents`, `.claude/settings.json` and a `.claude-plugin/plugin.json` manifest. There is no agent namespace, and unrecognized tool entries are "skipped silently". `SNOWFLAKE_HOME` moves the whole config tree, so each eval case can get an isolated config. (t4-snowflake-cortex-code-extensibility, t4-snowflake-cortex-code-plugins, t4-snowflake-cortex-code-settings)
- Snowflake ships an official Cortex Code Agent SDK (Python and TypeScript) that runs the `cortex` binary as a subprocess. Its result message has optional `total_cost_usd` and `usage` fields and it accepts model, effort and permission-mode options; there is no seed or temperature option. (t4-snowflake-cortex-code-agent-sdk)
- Snowflake's own evaluation features (Cortex Agent evaluations, TruLens, AI Observability) target native Cortex Agents and custom apps, not Cortex Code sessions. (t4-snowflake-cortex-agent-evaluations)
- The Agent Skills format is an open standard but only `name`, `description` and the body are portable; `allowed-tools` is experimental. Claude Code reads AGENTS.md only when no CLAUDE.md is on the path. Snowflake's docs never mention AGENTS.md. (t4-agentskills-specification, t4-agentsmd-site, t4-claude-code-memory-agentsmd)
- A skill's effect does not carry over unchanged between CLIs: the same skills gave different gains on Claude Code, Codex CLI and Gemini CLI, partly because of how each implements skills. (t4-skillsbench-arxiv-2602-12670, preprint; t4-anthropic-skill-best-practices)
- Existing multi-CLI eval runners share a design: one case file per skill, with-skill against without-skill runs, deterministic checks before LLM judges, several trials. None supports Cortex. Common failure causes: skills already installed on the host contaminating the comparison, flaky triggering, vendor terms of service, token counts that are not billing figures. (t4-eval-magic, t4-agent-exam-docs, t4-skillgrade-blog, t4-openai-eval-skills-blog)
- Record and replay usually works at the model API; Cortex's model calls go through Snowflake, so record the stream-json output and hook payloads instead, and sanitize account, user and host names, tokens, absolute paths and session ids. VCR.py documents the traps: encoded secrets slip past filters and short placeholders can corrupt unrelated text. A cross-CLI normalizer whose Claude adapter was only fixture-tested is a warning. (t4-docker-cagent-session-recording, t4-vcrpy-filtering, t4-codetalker-releases, t4-txcript)
- Contradictions with borg's measurements: Snowflake documents that the Cortex Code CLI is "not available on standard Snowflake trial accounts" but offers a dedicated trial; nothing documents that `--print` is refused on a trial, so that finding is undocumented, not contradicted. The docs say any agent `model` overrides the session model; borg measured that only a full model id is honored, and the docs' own example uses a full id. (t4-snowflake-cortex-code-cli-overview-trial, t4-snowflake-cortex-code-cli-reference)
- Not found: the schema of Cortex's stream-json events; whether the SDK works on a trial account; whether Cortex reads AGENTS.md; a per-call model id in Cortex output; any project that tests skills on Cortex; a measured study of a description tuned on one CLI and tried on another.
